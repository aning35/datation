# Auto Form Filling SOP

本技能用于处理“根据源数据填写目标模板/表单”的任务。

适用场景包括但不限于：

- 根据用户提供的信息填写 Word / Excel / Markdown / TXT 模板
- 根据合同、会议纪要、客户资料、项目资料填写信息表
- 根据源数据生成符合 JSON Schema 的 JSON
- 根据表格数据批量填充多个表单
- 根据已有材料填写申报表、申请表、登记表、核保信息表、项目情况表等

本技能的核心目标是：

> 忠实地把已有数据填入目标模板，不扩展、不审查、不臆造。

---

## 一、使用原则

### 1. 忠实填充

- 只填写源数据中明确存在、可合理推导或可计算得到的信息。
- 不得为了完成表单而编造数据。
- 不得擅自改变用户原始意思。
- 不得把不确定内容包装成确定结论。

### 2. 保持结构

- 优先保持目标模板的原有格式、字段顺序、表格结构、段落结构和文件类型。
- 只有当模板本身是纯文本或明确存在文本占位符时，才执行字符串替换。
- 对 Word、Excel、JSON、Markdown、HTML 等不同模板，应尽量按原结构填充，而不是强行转成纯文本。
- 表格、列表、重复行、嵌套结构应尽量保留原模板设计。

### 3. 最小必要校验

允许进行填表所必需的基础校验，例如：

- 字段是否缺失
- 类型是否匹配
- 日期格式是否正确
- 金额格式是否正确
- 枚举值是否在允许范围内
- 必填项是否为空
- 表格行数是否需要扩展
- JSON 是否符合 Schema

禁止进行超出填表目的的分析，例如：

- 法律审查
- 合规分析
- 商业判断
- 风险评级
- 审计分析
- 主观评价
- 策略建议

### 4. 缺失透明

- 源数据中没有的信息，不得猜测。
- 缺失字段应保留占位符、填入 `null`，或按模板要求留空。
- 必填字段缺失时，不得编造，应在缺失清单中列出。
- 多个来源存在冲突时，应记录冲突，不得擅自消除差异。

---

# 二、Workflow

执行层必须按以下 3 个核心步骤紧凑完成，不得膨胀为复杂分析任务。

---

## Step 1: 解析目标模板

读取目标表单、模板或 Schema，识别需要填充的内容。

需要提取：

- 字段名
- 占位符
- 必填字段
- 可选字段
- 枚举字段及允许值
- 日期、金额、数量等格式要求
- 表格、列表、重复行结构
- JSON Schema 的字段类型、必填项、默认值和约束
- Word / Excel / Markdown / HTML 等模板中的原始结构

输出一份简明字段清单。

示例：

```markdown
字段清单：
1. 公司名称
2. 统一社会信用代码
3. 法定代表人
4. 联系人
5. 联系电话
6. 项目名称
7. 投保人数
8. 保险期限
9. 风险说明
```

如用户只要求直接输出最终文件，可以不单独展示字段清单，但内部必须完成字段解析。

---

## Step 2: 匹配源数据并填充

读取用户提供的源数据，包括：

- 用户消息中的文本
- 上传的 Word / PDF / Excel / Markdown / TXT / JSON 文件
- 表格数据
- 合同
- 会议纪要
- 项目资料
- 客户资料
- 业务说明文档
- 非结构化材料

对每个目标字段进行匹配和填充。

---

### 2.1 直接匹配

当目标字段名与源数据字段完全一致或高度相似时，直接填入。

示例：

| 目标字段 | 源数据字段 | 处理方式 |
|---|---|---|
| 公司名称 | 公司名称 | 直接填入 |
| 联系电话 | 联系电话 | 直接填入 |
| 项目名称 | 项目名称 | 直接填入 |

---

### 2.2 同义匹配

允许识别常见同义表达。

示例：

| 目标字段 | 可匹配表达 |
|---|---|
| 公司名称 | 企业名称、单位名称、投保单位、客户名称 |
| 统一社会信用代码 | 信用代码、税号、纳税人识别号 |
| 联系人 | 经办人、对接人、负责人、联系人姓名 |
| 联系电话 | 手机号、电话、联系方式、联系电话 |
| 法定代表人 | 法人、法人代表、企业负责人 |
| 注册地址 | 企业地址、住所、注册地 |
| 项目名称 | 项目、项目标题、业务名称 |
| 保险期限 | 保障期限、承保期间、起止日期 |
| 投保人数 | 人数、员工人数、参保人数、被保人数 |

同义匹配应基于上下文判断，不能仅凭单个词强行匹配。

---

### 2.3 格式转换

根据模板要求进行必要格式转换。

常见转换包括：

- 日期格式转换  
  - `2026-06-05`
  - `2026年6月5日`
  - `2026/06/05`

- 金额格式转换  
  - `100000`
  - `100,000.00`
  - `人民币壹拾万元整`

- 百分比格式转换  
  - `0.15`
  - `15%`

- 数量格式转换  
  - `100`
  - `100人`
  - `共100人`

- 布尔值转换  
  - `true / false`
  - `是 / 否`
  - `有 / 无`

转换不得改变源数据含义。

---

### 2.4 计算填充

如字段需要通过源数据计算得到，可在本步骤内直接完成。

可计算内容包括：

- 合计金额
- 总人数
- 起止日期推算
- 税额
- 占比
- 平均值
- 明细汇总
- 分组统计
- 表格行汇总

示例：

```markdown
源数据：
员工人数：80人
临时工人数：20人

目标字段：
投保总人数 = 员工人数 + 临时工人数

填充值：
100人
```

计算过程应尽量简洁，不展开成复杂分析报告。

---

### 2.5 表格和列表填充

如果模板包含明细表，应按源数据行逐条填充。

处理规则：

- 源数据行数等于模板预留行：逐行填充。
- 源数据行数多于模板预留行：扩展表格行。
- 源数据行数少于模板预留行：保留空行或删除多余空行，视模板格式要求处理。
- 多个明细表应分别识别对应数据源。
- 嵌套列表应保持原层级结构。

示例：

| 姓名 | 证件号 | 岗位 | 保额 |
|---|---|---|---|
| 张三 | 320xxx | 电工 | 100万 |
| 李四 | 330xxx | 焊工 | 100万 |

---

### 2.6 枚举字段填充

枚举字段必须严格匹配允许值。

处理规则：

- 如果源数据值与枚举值完全一致，直接填入。
- 如果源数据表达与枚举值含义一致，可转换为模板允许值。
- 如果无法判断，不得强行选择，应标记为缺失或待确认。

示例：

| 模板允许值 | 源数据表达 | 填充值 |
|---|---|---|
| 是 / 否 | 已购买 | 是 |
| 男 / 女 | 男性 | 男 |
| A / B / C | 乙类 | B |
| 高 / 中 / 低 | 风险较高 | 高 |

不确定时：

```markdown
字段：风险等级
状态：无法判断
原因：源数据未提供明确风险等级，且模板枚举值为“高/中/低”
```

---

### 2.7 缺失字段处理

缺失字段不得臆造。

处理规则：

#### 文本 / Word / Markdown 模板

默认处理方式：

- 保留原占位符；或
- 留空；或
- 填写 `待补充`，仅当模板允许时使用。

示例：

```markdown
法定代表人：{{法定代表人}}
```

或：

```markdown
法定代表人：
```

#### JSON 输出

根据 Schema 要求处理：

- 可填 `null`
- 可填空字符串 `""`
- 可填空数组 `[]`
- 可省略字段
- 必填字段缺失时，优先使用 `null`，前提是 Schema 允许

示例：

```json
{
  "companyName": "某某科技有限公司",
  "legalRepresentative": null
}
```

#### 必填字段缺失

必须在缺失清单中列出。

示例：

```markdown
未填字段：
1. 法定代表人：源数据未提供
2. 营业期限：源数据未提供
3. 投保人数：源数据中未找到明确人数
```

---

### 2.8 冲突字段处理

当源数据中存在多个不同值时，不得擅自合并或编造。

处理规则：

- 优先选择来源更明确的值。
- 优先选择时间更新的值。
- 优先选择与模板上下文更相关的值。
- 无法判断时，保留占位符或填 `null`，并列入冲突清单。

示例：

```markdown
冲突字段：
1. 联系电话：
   - 来源A：13800000000
   - 来源B：13900000000
   - 处理：未填入，需用户确认
```

---

## Step 3: 生成最终文件

根据模板类型输出填充后的结果。

---

### 3.1 输出格式

优先保持原文件格式：

| 原模板类型 | 输出类型 |
|---|---|
| `.docx` | `.docx` |
| `.xlsx` | `.xlsx` |
| `.md` | `.md` |
| `.txt` | `.txt` |
| `.json` | `.json` |
| `.html` | `.html` |
| JSON Schema | 符合 Schema 的 `.json` |

只有在无法保留原格式时，才输出为 Markdown 或 TXT，并说明原因。

---

### 3.2 文件命名

默认命名规则：

```text
原文件名_filled.docx
原文件名_filled.xlsx
原文件名_filled.json
原文件名_filled.md
原文件名_filled.txt
```

如用户指定文件名，以用户要求为准。

---

### 3.3 JSON Schema 输出规则

如果目标是 JSON Schema，则必须：

- 严格符合 Schema。
- 字段类型正确。
- 必填字段完整处理。
- 枚举字段值必须在允许范围内。
- 不得输出 Schema 之外的字段，除非用户明确要求。
- 不得在 JSON 中添加注释。
- 不得混入 Markdown 解释文字，除非用户要求说明。

当用户要求直接展示 JSON 时，使用：

```json
{
  "field": "value"
}
```

---

### 3.4 缺失字段清单

如存在缺失、冲突或无法判断字段，应附简短清单。

示例：

```markdown
已完成表单填充。

输出文件：
- 项目信息表_filled.docx

未填字段：
1. 法定代表人：源数据未提供
2. 营业期限：源数据未提供

冲突字段：
1. 联系电话：源数据中存在两个不同号码，需确认
```

如用户明确要求“只输出最终文件，不要说明”，则只输出最终文件，但仍不得伪造缺失字段。

---

# 三、严格禁令

执行本技能时，必须遵守以下限制。

---

## 1. 禁止法律审查

不得进行以下工作：

- 合同风险审查
- 条款是否合法判断
- 法律责任分析
- 违约责任分析
- 法律修改建议
- 合同漏洞识别
- 法律合规评价

即使源数据是合同，本技能也只负责从合同中提取信息并填入表单。

---

## 2. 禁止业务扩展分析

不得主动进行以下工作：

- 商业可行性分析
- 风险评级
- 风控分析
- 财务分析
- 审计分析
- 合规审计
- 策略建议
- 经营诊断
- 管理咨询结论

除非用户另行明确要求，并切换到对应技能。

---

## 3. 禁止臆造数据

不得出现以下行为：

- 源数据没有的信息自行编写
- 无法计算的信息强行推导
- 无法判断的枚举值擅自选择
- 为了让表单完整而补充虚假内容
- 把不确定内容写成确定事实
- 把示例数据当成真实数据填入

---

## 4. 禁止改变模板意图

不得出现以下行为：

- 重写模板结构
- 删除关键字段
- 改变字段含义
- 改变字段顺序导致模板不可用
- 把表格改成段落
- 把用户原始表达改写成不同业务含义
- 擅自新增模板没有要求的字段

---

## 5. 禁止流程膨胀

Planner 应以以下 3 个步骤为主骨架：

1. 解析目标模板
2. 匹配源数据并填充
3. 输出最终文件

如确有必要，可在 Step 2 中内联处理：

- 计算
- 格式转换
- 表格扩展
- 枚举映射
- 缺失标记

不得将任务拆成冗长的多阶段研究、审查、报告生成流程。

---

# 四、默认输出风格

默认输出应简洁、直接、面向交付。

推荐格式：

```markdown
已完成表单填充。

输出文件：
- xxx_filled.docx

未填字段：
- 字段A：源数据未提供
- 字段B：枚举值无法判断
```

如果用户要求直接返回 JSON，则只返回 JSON，不添加解释性文字。

如果用户要求直接返回文件，则优先提供填充后的文件链接，并附最少说明。

---

# 五、触发示例

当用户提出以下请求时，应使用本技能：

- “根据这个合同帮我填一下信息表”
- “把这个 Excel 里的客户数据填进模板”
- “根据这份会议纪要生成项目申报表”
- “根据这些资料输出符合这个 JSON Schema 的 JSON”
- “帮我把这些字段填到 Word 模板里”
- “根据附件内容填写这张表”
- “把这个名单填入报名表”
- “根据客户资料生成核保信息表”
- “根据项目资料填申报模板”
- “根据合同内容提取甲乙方信息并填表”

---

# 六、非适用场景

以下任务不应使用本技能：

- 用户要求审查合同风险
- 用户要求判断条款是否合法
- 用户要求修改合同条款
- 用户要求分析商业可行性
- 用户要求做尽调报告
- 用户要求做合规审计
- 用户要求根据表单内容提出策略建议
- 用户要求生成正式研究报告
- 用户要求评估风险等级
- 用户要求提出谈判建议

这些任务应交由对应的合同审查、法律分析、商业分析、风险分析或报告写作技能处理。

---

# 七、边界说明

本技能可以做：

- 字段识别
- 数据映射
- 格式转换
- 表格填充
- JSON 结构生成
- 基础填表校验
- 缺失字段标记
- 冲突字段提示
- 输出填充后的文件

本技能不做：

- 法律判断
- 合规审查
- 风险分析
- 业务诊断
- 策略建议
- 价值判断
- 主观改写
- 虚构补全

一句话边界：

> 可以保证“填得对”，不能主动判断“内容好不好、合不合法、有没有风险”。

---

# 八、执行注意事项

1. 如果只有源数据、没有模板，应提示用户提供模板，或根据用户要求生成一个基础表单。
2. 如果只有模板、没有源数据，应提示用户提供源数据，或输出待填写版本。
3. 如果模板字段含义不清，应基于上下文尽量匹配；无法判断时标记为待确认。
4. 如果源数据中包含多个主体，应确认当前要填写哪个主体；无法确认时，分别输出多个版本或列出候选主体。
5. 如果用户要求批量填充，应为每条记录生成对应文件或对应 JSON 对象。
6. 如果用户要求保持格式，应优先保留原模板版式。
7. 如果用户要求快速完成，应减少解释，直接输出填充结果。
8. 如果用户要求可追溯，应附字段映射表，但不得扩展成审查报告。

---

# 九、字段映射表可选格式

当用户要求查看填充依据时，可以输出字段映射表。

示例：

| 模板字段 | 填充值 | 来源 | 处理方式 |
|---|---|---|---|
| 公司名称 | 某某科技有限公司 | 营业执照 | 直接匹配 |
| 联系电话 | 13800000000 | 客户资料 | 同义匹配 |
| 投保人数 | 100人 | 员工表 | 汇总计算 |
| 法定代表人 | 未填 | 无 | 源数据缺失 |

字段映射表属于填表过程说明，不属于审查报告。

---

# 十、质量检查清单

在输出最终文件前，执行最小必要检查：

- [ ] 所有模板字段均已识别
- [ ] 已填字段均可追溯到源数据或计算过程
- [ ] 未填字段未被臆造
- [ ] 枚举字段符合允许值
- [ ] 日期、金额、数量格式符合模板要求
- [ ] 表格行数与源数据匹配
- [ ] JSON 输出符合 Schema
- [ ] 输出文件格式尽量保持原模板格式
- [ ] 未进行法律、合规、风险或业务分析
