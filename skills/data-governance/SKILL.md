# 数据治理与指标体系建设标准作业程序  
# Data Governance & Metrics System SOP

## 1. 技能定位

本技能用于帮助企业、业务团队、数据团队或智能体系统建立标准化的数据治理能力和指标体系。

本技能主要回答：

- 企业应该如何建立指标体系？
- 一个业务指标应该如何定义、分层和管理？
- 多部门指标口径不一致怎么办？
- 数据质量如何检查、监控和治理？
- 数据血缘如何梳理？
- 主数据如何管理？
- 数据资产如何盘点和分级？
- 数据权限、安全、合规如何设计？
- 数据治理组织机制如何建立？
- 数据治理如何真正服务业务分析、预测建模和决策？

本技能强调：

- 先业务目标，后指标设计；
- 先统一口径，后建设报表；
- 先数据标准，后数据开发；
- 先责任归属，后质量问责；
- 先资产盘点，后资产治理；
- 先数据血缘，后影响分析；
- 先治理闭环，后平台工具；
- 不把数据治理做成纯文档工程；
- 不把指标体系做成指标堆砌。

## 3. 边界与防越界声明

### 3.1 本技能不是单纯的数据分析

本技能重点是：

- 定义数据；
- 管理数据；
- 治理数据；
- 统一口径；
- 建立标准；
- 保证质量；
- 明确责任；
- 支撑数据分析和建模。

它不直接替代：

- 具体数据分析；
- 异动归因；
- 预测建模；
- 因果分析；
- 算法训练；
- 报表开发；
- 系统实施。

当用户需要分析历史数据时，应衔接 `data-analysis`。  
当用户需要预测未来时，应衔接 `forecasting`。  
当用户需要因果归因时，应衔接 `deep-causal-analysis`。  
当用户需要看板和页面设计时，应衔接 `dashboard-design`。

---

### 3.2 本技能不得做出的错误承诺

不得承诺：

- “只要建数据中台，数据治理就完成了”；
- “只要统一指标字典，指标口径就不会冲突”；
- “只要上数据治理平台，数据质量就会自动变好”；
- “数据治理可以完全由技术团队单独完成”；
- “所有数据都必须统一到一个系统里”；
- “所有指标都应该越多越好”；
- “数据资产越多，价值越大”。

正确原则：

> 数据治理不是工具项目，而是业务、数据、技术、管理共同参与的长期机制。

---

### 3.3 数据治理与数据平台的关系

数据治理可以依托数据平台，但不等于数据平台。

数据平台解决：

- 数据采集；
- 数据存储；
- 数据加工；
- 数据计算；
- 数据服务；
- 数据展示。

数据治理解决：

- 数据有没有标准；
- 口径是否一致；
- 质量是否可信；
- 权限是否合规；
- 责任是否明确；
- 变更是否可控；
- 资产是否可查；
- 使用是否可追溯；
- 数据是否真正服务业务。

## 4. 核心执行原则

1. **先业务目标，后指标体系**  
   没有业务目标的指标体系，只是指标清单。

2. **先统一口径，后开发报表**  
   口径不统一时，越多报表只会制造更多冲突。

3. **先数据标准，后数据接入**  
   数据源接入前，应明确字段、码值、主键、时间、单位和命名标准。

4. **先数据 owner，后质量治理**  
   没有责任人的数据质量问题无法闭环。

5. **先核心数据，后全量治理**  
   数据治理应从高价值、高风险、高频使用的数据开始。

6. **先规则，后监控**  
   没有质量规则，就没有可执行的数据质量监控。

7. **先血缘，后变更**  
   修改字段、表、指标、任务前，必须评估影响范围。

8. **先分级分类，后权限控制**  
   不清楚数据敏感等级，就无法设计合理权限。

9. **先治理流程，后平台工具**  
   工具只能承载治理机制，不能替代治理机制。

10. **先应用闭环，后资产沉淀**  
   数据治理最终必须服务分析、运营、风控、经营管理和业务决策。

## 6. 标准工作流

## 步骤 1：治理目标与业务场景定义

### 1.1 明确治理目标

首先确认数据治理要解决什么问题。

常见目标：

- 统一指标口径；
- 提升数据质量；
- 打通数据孤岛；
- 建立数据资产目录；
- 提高数据使用效率；
- 降低报表重复建设；
- 支撑经营分析；
- 支撑预测建模；
- 支撑风控决策；
- 满足监管合规；
- 保障数据安全；
- 建立数据责任机制。

错误做法：

> 一上来就设计数据表、数据平台、数据字典，而没有明确业务治理目标。

正确做法：

> 先明确业务痛点，再设计治理对象、范围、优先级和落地路径。

---

### 1.2 明确治理范围

需要确认：

- 治理的是一个指标、一个报表、一个业务域，还是全公司；
- 涉及哪些部门；
- 涉及哪些系统；
- 涉及哪些数据源；
- 涉及哪些指标；
- 涉及哪些报表；
- 涉及哪些数据使用场景；
- 是否涉及敏感数据；
- 是否涉及外部共享；
- 是否涉及监管要求。

---

### 1.3 明确业务场景

数据治理必须绑定业务使用场景。

典型业务场景：

- 经营分析；
- 销售管理；
- 用户增长；
- 客户运营；
- 风险控制；
- 财务管理；
- 供应链管理；
- 客服质检；
- 保险承保；
- 理赔管理；
- 安全生产；
- 投放优化；
- 库存管理；
- 绩效考核；
- 管理驾驶舱。

---

### 1.4 明确治理优先级

优先治理以下数据：

1. 高频使用数据；
2. 核心经营指标；
3. 多部门共用指标；
4. 经常争议的指标；
5. 高风险敏感数据；
6. 监管要求数据；
7. 影响决策的数据；
8. 影响结算、财务、风控、考核的数据；
9. 支撑算法建模的数据；
10. 质量问题高发的数据。

## 步骤 3：指标体系设计

### 3.1 指标体系建设原则

指标体系必须满足：

1. **业务目标牵引**  
   指标必须服务业务目标，而不是简单堆砌数据。

2. **分层清晰**  
   从战略指标到过程指标逐层拆解。

3. **口径唯一**  
   同一指标在同一业务语境下只能有一个标准口径。

4. **可解释**  
   业务方能理解指标含义和使用边界。

5. **可计算**  
   指标必须有明确数据来源和计算逻辑。

6. **可追溯**  
   指标能追溯到字段、表、任务和系统。

7. **可维护**  
   指标变更有流程、有版本、有通知。

8. **可行动**  
   指标变化能触发具体业务动作。

---

### 3.2 指标分层

推荐使用以下分层：

#### L0：北极星指标

反映业务最终价值。

示例：

- GMV；
- 净收入；
- 活跃客户数；
- 有效保费；
- 续保率；
- 赔付率；
- 客户生命周期价值；
- 风险调整后利润。

#### L1：结果指标

反映业务结果。

示例：

- 销售额；
- 订单量；
- 新增客户数；
- 支付用户数；
- 留存率；
- 投诉率；
- 毛利率；
- 成交率。

#### L2：过程指标

反映业务过程。

示例：

- 曝光量；
- 点击量；
- 到访量；
- 报价量；
- 询盘量；
- 下单量；
- 支付成功率；
- 核保通过率；
- 理赔处理时效。

#### L3：诊断指标

用于定位问题。

示例：

- 各渠道转化率；
- 各地区投诉率；
- 各版本崩溃率；
- 各商品缺货率；
- 各销售人员成交率；
- 各医院赔付异常率。

#### L4：动作指标

用于驱动业务动作。

示例：

- 待跟进客户数；
- 高风险订单数；
- 待处理工单数；
- 超时理赔案件数；
- 库存预警 SKU 数；
- 高流失风险用户数。

---

### 3.3 指标类型

指标可分为：

1. **规模类指标**
   - 销售额；
   - 用户数；
   - 订单量；
   - 保费收入；
   - 案件数。

2. **效率类指标**
   - 转化率；
   - 成交率；
   - 处理时效；
   - 人效；
   - 周转率。

3. **质量类指标**
   - 投诉率；
   - 退款率；

### 3.5 指标口径示例

#### GMV

```text
指标名称：GMV

业务定义：
统计周期内用户提交并支付成功的订单总金额。

计算公式：
GMV = sum(支付成功订单金额)

时间口径：
按支付成功时间统计。

过滤条件：
剔除测试订单、取消订单、未支付订单。

退款处理：
默认不扣除退款金额。如需扣除退款，应使用“净 GMV”。

统计粒度：
日、周、月、渠道、商品、地区。

数据来源：
订单表、支付表。

注意：
GMV 不等于收入，不等于利润。
```

#### 转化率

```text
指标名称：下单转化率

业务定义：
访问用户中完成下单行为的用户比例。

计算公式：
下单转化率 = 下单用户数 / 访问用户数

分子：
统计周期内至少完成一次下单的去重用户数。

分母：
统计周期内至少访问一次页面的去重用户数。

去重规则：
按 user_id 去重。

时间口径：
按访问发生时间归属周期。

注意：
如果用户跨周期访问和下单，需要明确归因窗口。
```

## 步骤 5：数据质量治理

### 5.1 数据质量维度

数据质量至少包含以下维度：

1. **完整性**
   - 是否缺字段；
   - 是否缺记录；
   - 是否缺时间分区；
   - 是否缺关键值。

2. **准确性**
   - 数据是否真实反映业务；
   - 金额、数量、状态是否正确；
   - 是否与源系统一致。

3. **一致性**
   - 跨系统口径是否一致；
   - 同一字段含义是否一致；
   - 主数据映射是否一致。

4. **唯一性**
   - 主键是否重复；
   - 订单是否重复；
   - 用户是否重复；
   - 事件是否重复上报。

5. **及时性**
   - 数据是否按时到达；
   - 是否存在延迟；
   - 是否存在回填。

6. **有效性**
   - 字段是否符合类型；
   - 码值是否有效；
   - 时间是否合理；
   - 金额是否非负。

7. **稳定性**
   - 数据波动是否异常；
   - 任务是否稳定；
   - 口径是否稳定。

8. **可追溯性**
   - 数据能否追溯来源；
   - 计算过程是否可查；
   - 变更是否可追踪。

---

### 5.2 数据质量规则

常见质量规则：

```text
非空规则：
- order_id 不可为空
- user_id 不可为空
- pay_time 在支付成功订单中不可为空

唯一性规则：
- order_id 在订单表中必须唯一

枚举规则：
- order_status 只能为 created、paid、cancelled、refunded

范围规则：
- order_amount >= 0
- discount_rate between 0 and 1

时间规则：
- pay_time >= create_time
- refund_time >= pay_time

一致性规则：
- 支付表支付成功金额应等于订单表支付金额
- 用户主表 user_id 应能关联到行为日志 user_id

波动规则：
- 日订单量环比波动超过 50% 触发预警
- 支付成功率低于近 30 日均值 3 个标准差触发预警
```

---

### 5.3 数据质量分级

可将质量问题分为：

#### P0：严重阻断

影响核心经营指标、财务、风控、监管或关键决策。

处理要求：

- 立即告警；
- 暂停下游使用；
- owner 立即修复；
- 输出事故报告。

#### P1：高优先级

影响核心报表、重要看板或模型结果。

处理要求：

- 当日处理；
- 通知相关使用方；
- 记录修复过程。

#### P2：中优先级

影响局部分析或非核心数据。

处理要求：

- 排期修复；
- 定期跟踪。

#### P3：低优先级

不影响核心业务，但影响数据规范性。

处理要求：

- 纳入治理 backlog；
- 后续优化。

---

### 5.4 数据质量闭环

质量治理必须形成闭环：

1. 发现问题；
2. 识别影响范围；
3. 定位责任 owner；
4. 分析根因；
5. 制定修复方案；
6. 修复数据；
7. 验证结果；
8. 通知下游；
9. 记录问题；
10. 建立防复发规则。

不得只做质量检查而不处理问题。

- 规则通过率；

- 异常字段数量；

## 14. 数据治理高发陷阱防御清单

| 陷阱 | 表现形式 | 防御方法 |
|---|---|---|
| 工具替代治理 | 以为买平台就完成治理 | 先建标准、流程、owner，再上工具 |
| 指标堆砌 | 指标很多，但没有业务逻辑 | 按业务目标和指标树分层设计 |
| 口径不统一 | 同一指标多个部门多个算法 | 建立唯一指标字典和评审机制 |
| 没有 owner | 数据出问题无人负责 | 每个核心数据和指标指定业务 owner 与技术 owner |
| 只建文档不落地 | 标准写完没人用 | 将标准嵌入开发、报表、权限和质量流程 |
| 只治理技术不治理业务 | 数据团队单独推进，业务不参与 | 指标口径必须由业务 owner 确认 |
| 全量治理起步 | 一开始想治理所有数据 | 从核心指标、高频数据、高风险数据开始 |
| 忽视数据血缘 | 字段变更导致大量报表错误 | 建立字段、指标、报表血缘 |
| 质量检查无闭环 | 发现问题但无人处理 | 建立告警、工单、修复、复盘流程 |
| 权限粗放 | 所有人都能看敏感数据 | 分级分类、最小权限、审批和审计 |
| 主数据混乱 | 一个客户多个 ID | 建立主数据标准、匹配和合并规则 |
| 历史不可追溯 | 指标口径变更后无法解释历史差异 | 建立指标版本和变更记录 |
| 报表重复建设 | 多个部门做同类看板 | 建立报表资产目录和复用机制 |
| 只关注存储不关注使用 | 数据很多但没人用 | 评估使用频率、业务价值和资产热度 |
| 忽视生命周期 | 过期数据和无用报表长期存在 | 建立归档、下线和删除机制 |
| 忽视合规 | 敏感数据随意导出 | 建立数据分级、脱敏、审计和审批机制 |
| 治理没有考核 | 没有组织机制，无法持续 | 建立治理指标和责任考核 |
| 标准过度复杂 | 标准太重，业务无法执行 | 分阶段、轻量化、可落地推进 |
| 忽略 AI/模型使用 | 模型特征没有血缘和质量监控 | 将模型特征纳入数据资产和质量治理 |
| 数据治理形式化 | 只有制度，没有业务效果 | 用看板准确率、取数效率、质量问题下降衡量效果 |

## 21. 结语

本技能的核心价值不是“整理一份数据字典”，而是建立一套可持续运行的数据治理机制。

它要防止：

- 指标口径混乱；
- 数据重复建设；
- 数据质量无人负责；
- 数据资产不可见；
- 数据变更不可控；
- 数据权限粗放；
- 数据孤岛长期存在；
- 数据治理停留在文档层面；
- 数据无法支撑分析、预测和决策。

最终目标是让企业的数据做到：

- 找得到；
- 看得懂；
- 信得过；
- 管得住；
- 用得好；
- 可追溯；
- 可复用；
- 可运营；
- 可持续创造业务价值。
